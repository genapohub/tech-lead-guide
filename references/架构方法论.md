# 技术负责人 / 架构师方案产出指南 · 领域方法论

> 本文档是 `tech-lead-guide` 技能的领域知识库。

---

## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 技术体系搭建 | 全新产品/业务线、需从零定义技术栈、架构风格、工程规范 | 10-12类 | 4-8周 |
| 场景二 | 中型技术决策/改造 | 跨栈技术选型、架构模块重构、技术债务治理 | 6-8类 | 2-4周 |
| 场景三 | 单点决策/技术评审 | 单一技术方案评审、小范围架构调整、技术风险评估 | 2-3类 | 1-3天 |
| 场景四 | 大版本架构演进 | 架构风格变更(单体→微服务)、技术栈全面升级、遗留系统现代化 | 8-10类 | 6-12周 |
| 场景五 | 技术预研/战略规划 | 新技术方向探索、技术雷达更新、长期技术战略 | 3-4类 | 2-4周 |

### 识别流程

```
是否全新产品线/无技术体系？ → 是 → 场景一
    ↓否
是否架构风格变更/技术栈全面升级？ → 是 → 场景四
    ↓否
是否为战略规划/技术雷达更新？ → 是 → 场景五
    ↓否
是否涉及跨栈多技术决策/多模块重构？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 技术体系搭建（12类产出）

### 战略与选型
1. **业务与技术对齐分析** — 业务目标→非功能需求映射、可用性/可扩展性/安全性/性能要求、合规约束
2. **技术选型方案** — 全栈技术栈决策（前端/后端/数据/基础设施）、选型理由与权衡、Make vs Buy决策、技术风险矩阵
3. **架构风格决策** — 架构风格选择（单体/微服务/事件驱动/CQRS/Serverless）、决策依据、适用边界

### 架构设计
4. **系统架构设计** — C4模型（Context→Container→Component）、部署拓扑、服务通信拓扑、数据流图、技术架构约束
5. **数据架构设计** — 数据存储选型（关系型/文档/图/时序/缓存）、数据分片策略、读写分离、数据一致性方案
6. **安全架构设计** — 纵深防御模型、认证授权体系、数据安全分级、安全通信、审计追踪
7. **非功能性需求方案** — 可扩展性（水平/垂直）、可用性（SLA/SLO）、性能（容量规划）、可观测性（监控/日志/追踪）

### 工程规范
8. **编码规范与质量门禁** — 代码规范、Code Review流程、质量门禁（Lint/Test/Coverage/Security）、分支策略（GitFlow/Trunk-Based）
9. **工程化规范** — Monorepo vs Polyrepo、模块化设计原则、API设计规范、文档规范、版本管理
10. **团队技术能力规划** — 技能矩阵评估、培训计划、招聘优先级、技术导师制度
11. **技术雷达与创新管理** — 技术分类（采用/试验/评估/暂缓）、技术雷达更新机制、创新时间分配
12. **架构决策记录(ADR)** — ADR模板、决策编号体系、决策追溯、定期Review机制

## 三、场景二：中型技术决策/改造（6-8类产出）

1. **问题定义** — 当前技术问题描述、业务影响量化、改造必要性论证
2. **方案对比分析** — 候选方案（≥2个）、多维度对比（技术/成本/风险/团队匹配/时间）、推荐方案
3. **架构设计** — 目标架构图、与现有架构关系、数据流变化、接口兼容性
4. **技术债务评估** — 当前技术债务清单、优先级排序（影响×修复成本）、偿还计划
5. **实施路线图** — 分阶段推进计划、里程碑、依赖关系、资源需求
6. **风险评估与缓解** — 技术风险/团队风险/进度风险、缓解措施、应急预案
7. **团队影响评估** — 技能要求变化、培训需求、工作量分配
8. **ADR记录** — 决策背景、方案对比、最终决策、后果

---

## 四、场景三：单点决策/技术评审（2-3类产出）

1. **决策分析** — 问题背景、候选方案对比（含不做方案）、推荐结论
2. **ADR记录** — 架构决策记录
3. **风险评估** — 决策风险点、缓解措施

---

## 五、场景四：大版本架构演进（8-10类产出）

1. **架构评估报告** — 现状架构痛点分析、演进必要性、预期收益
2. **目标架构设计** — 目标架构图（C4）、新旧架构对比、渐进式演进路径
3. **技术栈迁移方案** — 新旧技术对照、迁移策略（Strangler Fig/平行运行/大爆炸）、回滚方案
4. **数据迁移方案** — 数据模型变更、迁移步骤、双写/双读过渡、一致性校验
5. **兼容性方案** — API兼容策略、客户端迁移指南、弃用时间线
6. **性能容量规划** — 新旧架构性能对比、资源需求、扩容计划
7. **技术债务清零计划** — 存量技术债务处理方案（迁移中偿还/迁移后偿还/标记废弃）
8. **团队转型计划** — 新技能培训、渐进式职责转移、外部咨询/招聘
9. **风险与回滚预案** — 架构回滚可行性、数据回滚方案、业务连续性保障
10. **效果评估** — 迁移前后关键指标对比（性能/可用性/开发效率/运维成本）

---

## 六、场景五：技术预研/战略规划（3-4类产出）

1. **技术趋势分析** — 行业技术趋势、竞品技术栈分析、技术雷达更新建议
2. **候选方案调研** — 新技术调研报告、社区活跃度、团队适配度
3. **PoC验证** — 核心场景验证、已知限制、性能基准
4. **战略建议** — 技术方向推荐、投资优先级、风险提示

## 七、架构通用规范

### ADR 模板
```markdown
# ADR-{序号}: {标题}

## 状态
{提议中/已接受/已废弃/已替代}

## 背景
为什么需要这个决策？

## 决策
我们决定做什么？

## 后果
正面影响 / 负面影响 / 风险

## 替代方案
考虑过但不采用的方案及原因
```

### 技术选型评估维度
| 维度 | 权重 | 说明 |
|------|:---:|------|
| 功能匹配 | 30% | 是否满足核心需求 |
| 性能 | 20% | 吞吐/延迟/资源消耗 |
| 社区生态 | 15% | 活跃度/文档/第三方集成 |
| 团队匹配 | 15% | 学习成本/现有经验 |
| 运维成本 | 10% | 部署/监控/升级 |
| 商业风险 | 10% | 许可证/供应商锁定/长期支持 |

### 架构评审 Checklist
- [ ] 是否满足非功能需求（性能/安全/可用性/可扩展性）
- [ ] 是否存在单点故障
- [ ] 数据一致性方案是否明确
- [ ] 安全纵深防御是否完整
- [ ] 是否有容量规划和扩容方案
- [ ] 监控可观测性是否覆盖
- [ ] 回滚/降级方案是否可行
- [ ] 是否产生新的技术债务

## 八、产出质量检查清单

- [ ] 业务目标与技术方案对齐
- [ ] 技术选型有明确的权衡分析
- [ ] 架构图清晰（C4模型）
- [ ] 非功能需求有具体指标（SLA/SLO/性能目标）
- [ ] ADR记录完整可追溯
- [ ] 技术债务有清单+优先级+偿还计划
- [ ] 安全架构覆盖纵深防御
- [ ] 容量规划有数据支撑
- [ ] 回滚/降级方案可行
- [ ] 团队能力与方案匹配

### 去AI味检查
- [ ] 架构方案中有"团队实际情况"的约束——不只有理想方案，有"我们现在的团队能做出来什么"
- [ ] 技术选型不只有推荐，有备选方案和被否决的方案
- [ ] 至少有 1 处"微服务/DDD/MQ 这些业界流行方案在我们场景下是过度设计"的判断
- [ ] ADR 不只有"为什么选A"——有"A的最大风险是什么、什么时候会后悔"

## 十、超越AI味：技术负责人的真实判断

> AI 能画出完美的架构图，但真正的技术负责人做的是 trade-off——用有限的团队能力、有限的时间、有限的钱，做出当前最优的决定。

### 10.1 反AI架构决策五条

**1. 架构从团队能力出发，不是从技术潮流出发**

- 错误做法: "建议采用微服务架构 + DDD + Event Sourcing + CQRS"
- 正确做法: "团队3个后端，1个熟悉Go、2个熟悉Python。选择 Python/FastAPI 单体架构 + 模块化——团队能掌握、能维护、能快速迭代"

**2. 每个选型都要写"什么时候会后悔"**

- 错误做法: "选 MySQL 因为成熟稳定社区活跃"
- 正确做法: "选 MySQL -> 后悔场景：如果未来需要存储大量非结构化日志（那时考虑引入 MongoDB）。选 Redis -> 后悔场景：如果数据量超内存（那时考虑换 Pika/Tendis）"

**3. 技术债不是"以后还"，是"算好利息再借"**

- "快速上线阶段接受 SQL 查询无索引（利息：P95 从 50ms 升到 200ms，可接受），在用户量达到 1 万前还清（建索引，预估 0.5 人天）"

**4. 非功能需求必须量化到数字**

- 错误做法: "系统需要高可用、高性能"
- 正确做法: "可用性：99.9%（月不可用 < 43 分钟）。性能：P95 接口响应 < 500ms。扩展性：支撑日活 10 万（当前 1 万）"

**5. "过度设计"不是谦虚，是浪费**

- "当前阶段只需要 3 个模块 + 1 个DB + 1 个 Redis。等 XX 场景出现时再拆分"

### 10.2 技术选型的"反光鲜"检查

| 如果你选了... | 问自己... | 如果答案是"不确定"，先不要引入 |
|-------------|----------|------------------------------|
| 微服务 | 有没有 3 个独立团队需要独立部署？ | 单体 + 模块化足够 |
| K8s | 有没有 10+ 个服务需要编排？ | Docker Compose 够用 |
| 消息队列 | 有没有超过 1 秒的异步处理？ | 数据库轮询/定时任务够用 |
| GraphQL | 前端是不是要跨多个微服务取数据？ | RESTful + BFF 更简单 |
| gRPC | 是不是微服务间有超高频调用？ | RESTful + JSON 团队更熟悉 |

---

_技术负责人的价值 = 用最小的复杂度解决最大的问题，让团队三年后回头看时说"当年的决策没有坑我们"。_
